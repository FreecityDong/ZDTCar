# ESP32-S3 + Emm_V5.0 双闭环步进 + MPU6050 平衡小车技术方案

## 1. 目标与边界

本项目采用 Arduino 框架，主控为 ESP32-S3，执行机构为 2 个 Emm_V5.0 闭环步进电机，姿态传感器为 MPU6050，目标是实现两轮自平衡小车的基础闭环控制，并为后续加入遥控、里程计、路径控制预留接口。

本方案优先目标：

1. 先把车稳定立住。
2. 在稳定立住的基础上实现前后移动和原地转向。
3. 保持硬件和软件结构可扩展，后续可加入遥控、OLED、蓝牙/Wi-Fi、上位机调参。

本方案默认你当前阶段做的是 `V1 原型机`，优先可调试性，不追求一次性做到最简 BOM 或最强抗干扰。

## 2. 从资料中提炼出的关键结论

根据本地资料：

- 驱动供电范围为 `12V~32V`。
- 驱动支持 `TTL 串口 / RS232 / RS485 / CAN / 脉冲` 控制。
- 串口/RS485/CAN 多机地址范围为 `1~255`，`0` 为广播地址。
- 串口控制默认校验为固定 `0x6B`，也支持 `XOR / CRC-8 / Modbus`。
- 速度模式命令为 `0xF6`，位置模式命令为 `0xFD`，立即停止命令为 `0xFE`。
- 支持多机同步缓存命令后用 `0xFF` 触发同时动作。
- 可读取实时转速 `0x35`、实时位置 `0x36`、状态标志位 `0x3A`、系统状态 `0x43`。
- 通讯速度默认 `115200`，支持更高波特率到 `921600`。
- 驱动支持开环/闭环模式切换，闭环模式最高转速可到 `3000RPM+`。
- 可设置堵转保护、电流限制、位置到达窗口、回零参数等。

## 3. 通讯方案选择

### 3.1 推荐方案

`V1 原型机` 推荐先用 `TTL 串口多机总线`，而不是一上来就上 RS485 或 CAN。

原因：

1. 资料里已经明确支持 `TTL 串口多机通讯`，接线和例程最直接。
2. 你当前是 `ESP32-S3 + Arduino`，直接用硬件串口最快落地。
3. 平衡车原型阶段调试重点在控制算法，不应该先把复杂度花在总线收发器和总线时序上。
4. 双电机距离主控通常很近，只要电源地规划正常，TTL 在原型机上通常足够。

### 3.2 何时升级到 RS485

满足下面任一条件，再切到 `RS485`：

1. 电机线和主控线较长，串口误码明显。
2. 电机启停时 IMU 或串口经常受干扰。
3. 小车结构紧凑但电机电流大，地弹噪声明显。
4. 后续准备做外壳量产或更复杂整车布线。

结论：

- `第一版先用 TTL`
- `第二版抗干扰不够再换 RS485`

软件层面可以抽象成统一 `MotorBus` 接口，后续切 RS485 不需要推翻控制代码。

## 4. 总体系统架构

### 4.1 硬件分层

1. 动力层：2 个 Emm_V5.0 闭环步进电机
2. 控制层：ESP32-S3
3. 传感层：MPU6050
4. 电源层：电机母线电源 + 5V/3.3V 降压
5. 安全层：急停、欠压、倾倒保护、通信超时保护

### 4.2 控制分层

建议采用三层控制：

1. 最内层：电机驱动自身闭环
2. 中间层：车体平衡环
3. 外层：速度/位移/转向环

解释：

- 电机驱动器内部已经做了电机闭环，不要在 ESP32 上重复做“电流环/相位环”。
- ESP32 主要负责“整车姿态控制”，把左右轮目标速度发给两个电机。
- 因此本项目的执行命令首选 `速度模式`，不建议把平衡主控制建在位置模式上。

## 5. 硬件方案

### 5.1 主控

当前工程已经配置为：

- 板卡：`esp32-s3-devkitc1-n16r8`
- 框架：`Arduino`

对应配置文件：

- [platformio.ini](/Users/hahadong/Documents/PlatformIO/Projects/ZDTCar/platformio.ini)

### 5.2 传感器

MPU6050 使用 I2C 连接。

建议连接：

- `SDA -> GPIO8`
- `SCL -> GPIO9`
- `INT -> GPIO4`，可选，但建议预留
- `VCC -> 3.3V`
- `GND -> GND`

说明：

- ESP32-S3 的 I2C 管脚可重映射，上述只是建议值。
- 如果你板子已有固定外设占用，再调整为其它普通 GPIO 即可。

### 5.3 电机通讯

推荐使用 `UART1` 作为电机总线。

建议连接：

- `Motor_TX -> GPIO18`
- `Motor_RX -> GPIO17`
- 两个电机的通信口并联到同一组 UART
- 所有设备 `GND 共地`

如果切 RS485，则增加：

- `DE/RE -> GPIO16`
- 外挂 `3.3V 兼容 RS485 收发器`

### 5.4 电源方案

建议分成两路：

1. 动力母线：给 Emm_V5.0 驱动供电，范围 `12V~32V`
2. 控制电源：从动力母线降压出 `5V`，再给 ESP32-S3 和 MPU6050 提供 `5V/3.3V`

建议：

- 原型机优先选 `24V` 母线，动态响应更好。
- 如果你电机规格偏小，也可先用 `4S 锂电` 试做，但需要确认加速力矩是否足够。
- 电机电源和主控电源不要直接混在细线面包板上供电。
- 主控地和驱动地只做可靠共地，不要让大电流回路经过 IMU 地线。

### 5.5 机械布局建议

平衡车是否好调，很大程度取决于机械结构，而不只是 PID。

建议：

1. 电池尽量靠下放，降低整体抖动。
2. 质心要位于轮轴上方，但不要太高。
3. IMU 尽量靠近车体中心，远离电机和大电流线。
4. 左右轮结构、轮胎材质、轮径尽量一致。
5. 电机安装座必须足够刚，避免柔性振动干扰姿态环。

## 6. 驱动参数配置建议

两个电机出厂后，建议先单独上位机检查，再接入主控。

### 6.1 基础配置

每台电机建议设置：

1. `ID_Addr` 分别设为 `1` 和 `2`
2. `P_Serial = UART_FUN`
3. `Checksum = 0x6B`
4. `UartBaud = 256000` 或 `512000`
5. `Response = Receive`
6. `控制模式 = 闭环模式`
7. `Clog_Pro = Enable`

说明：

- 第一阶段用 `0x6B` 最省事，直接兼容资料里的例程。
- 波特率不建议一直停留在 `115200`，平衡车更看重控制链路延迟，建议至少 `256000`。
- `Response` 开发阶段用 `Receive` 便于排障，后续稳定后可改为 `None` 以减轻总线负载。

### 6.2 运行模式选择

平衡车主控制命令建议使用：

- 日常闭环控制：`速度模式 0xF6`
- 紧急刹车：`立即停止 0xFE`
- 调试标定：按需读取 `0x35 / 0x36 / 0x3A / 0x43`

不建议把平衡主环建立在位置模式上，原因是：

1. 平衡控制本质上更接近“连续速度调节”。
2. 位置模式更适合云台、转盘、定角度定位，不适合持续倒立修正。
3. 频繁发送位置目标会引入额外轨迹解释成本，不如速度模式直接。

### 6.3 平衡车专用速度控制参数建议

Emm_V5.0 的速度模式自带内部加减速参数 `acc`。根据说明书，`acc = 0` 表示直接启动，`acc = 1~255` 表示启用曲线加减速，因此它会直接改变执行机构的动态响应。

对平衡车来说，电机不是在做普通“平滑加速”，而是在持续纠正即将倾倒的车体，所以参数目标应当优先保证“跟手”，而不是“好看”。

建议参数如下：

1. `速度模式命令 = 0xF6`
2. `acc = 0` 作为平衡调试初始值
3. `Response = Receive` 作为开发阶段默认值
4. `UartBaud = 256000` 起步，优先推荐 `512000`
5. `Checksum = 0x6B`
6. `Clog_Pro = Enable`
7. `S_Vel_IS = Disable`
8. `控制模式 = 闭环模式`

原因说明：

- `acc = 0` 时，ESP32 输出的目标速度会尽快作用到电机，更适合姿态内环调试。
- 如果 `acc` 设得过小但不为 0，驱动内部会额外插入速度爬升过程，相当于给平衡环串了一个滞后环节。
- `S_Vel_IS = Disable` 可以避免速度单位缩小 10 倍后，让调参与日志观察变得不直观。
- 波特率过低会让双电机串口控制产生额外延迟，平衡控制会显得“肉”。

建议分阶段设置：

#### 第一阶段：先立住

目标是让车先能站住，不追求平顺。

- `acc = 0`
- `Response = Receive`
- `状态读取频率 = 20~50Hz`
- `速度命令刷新频率 = 150~200Hz`

这一阶段的原则是：

- 姿态环优先
- 少读状态，多发命令
- 先不要为了“电机柔和”而增加内部加减速

#### 第二阶段：立住后减振

如果已经能稳定站立，但出现明显齿感、抖动、轮子动作过硬，可以尝试少量引入平滑。

建议尝试顺序：

1. 先保持 `acc = 0`，通过减小姿态环增益来观察
2. 再尝试 `acc = 240~255`
3. 如果响应仍足够快，再视情况微调

不建议一开始就用：

- `acc = 10`
- `acc = 20`
- `acc = 50`

这些值更像普通运动控制参数，通常会明显拖慢平衡车的纠偏速度。

#### 第三阶段：加入外环速度控制

当车已经能稳定站立后，加入前进/后退速度环，此时仍然建议：

- 电机命令层保持“快响应”
- 外层速度环慢一些

推荐思路：

1. 内层姿态环继续使用 `acc = 0`
2. 外层速度 PI 通过“目标倾角偏置”或“目标轮速偏置”工作
3. 不要把平滑任务交给电机内部加减速

### 6.4 平衡车调参时的推荐观察量

调 Emm_V5.0 时，不要只看“车有没有动”，建议同时打印这些量：

1. `pitch`
2. `gyro`
3. `left_rpm_target`
4. `right_rpm_target`
5. `left_rpm_actual`
6. `right_rpm_actual`
7. `motor_state_flag`

如果发现：

- `目标 RPM` 变化很快
- `实际 RPM` 跟随明显慢半拍

优先检查：

1. `acc` 是否不是 0
2. 波特率是否仍为 `115200`
3. 是否每个控制周期都在等返回帧
4. 是否状态轮询过于频繁

### 6.5 一组可直接开调的初始建议值

以下是一组偏保守、适合原型调试的起始值：

- `UartBaud = 512000`
- `Checksum = 0x6B`
- `Response = Receive`
- `acc = 0`
- `控制周期 = 5ms`
- `电机速度命令刷新 = 200Hz`
- `电机状态轮询 = 50Hz`
- `堵转保护 = Enable`
- `速度限幅 = ±300~600 RPM` 先起步，再逐步放宽

其中 `速度限幅` 不是驱动内部参数，而是建议你在主控软件里先做人为限幅，避免调试初期车一抖就把轮子打到很高转速。

## 7. 控制策略

### 7.1 推荐控制链路

推荐采用：

`MPU6050姿态估计 -> 平衡控制器 -> 左右轮目标RPM -> 电机速度模式`

### 7.2 姿态估计

MPU6050 建议使用：

1. 陀螺仪积分得到短时角度变化
2. 加速度计估计重力方向
3. 使用 `互补滤波` 做第一版姿态融合

第一版不建议一开始就上复杂 EKF，原因很简单：平衡车先要尽快立住，互补滤波更容易定位问题。

推荐控制量：

- `pitch`：俯仰角
- `gyro_y` 或对应俯仰轴角速度

### 7.3 控制环结构

建议先做两环：

1. `姿态 PD/PID 环`
2. `车速 PI 环`

控制输出示意：

```text
u_balance = Kp_a * angle + Kd_a * gyro + Ki_a * angle_integral
u_speed   = Kp_v * speed_error + Ki_v * speed_integral
u_turn    = Kp_t * yaw_cmd

left_rpm_target  = u_balance + u_speed - u_turn
right_rpm_target = u_balance + u_speed + u_turn
```

建议第一版先不做完整偏航闭环，只保留一个转向输入项 `u_turn`。

### 7.4 速度反馈来源

车轮速度不要只靠“发给电机的目标速度”估算，应该结合驱动返回的实时速度：

- 读取 `0x35` 获取实时 RPM
- 左右轮平均值得到底盘线速度估计

这样外环速度控制会明显更稳。

### 7.5 控制周期建议

建议初始控制频率如下：

1. IMU 采样：`500Hz`
2. 姿态解算：`500Hz`
3. 电机目标速度刷新：`200Hz`
4. 电机状态轮询：`50Hz`
5. 遥控/上位机/日志：`20Hz`

原因：

- MPU6050 原始数据采样频率可以高一些。
- 串口总线要给两个电机发命令并处理返回，`200Hz` 是比较稳妥的初始值。
- 等系统稳定后，再评估是否上调到 `250Hz~400Hz`。

## 8. 通讯时序建议

### 8.1 第一版建议

控制环每周期按以下顺序：

1. 读取最新 IMU 数据
2. 计算左右轮目标 RPM
3. 分别给 1 号、2 号电机发送速度模式命令
4. 不在每个控制周期都读状态

这种方式最简单，通常就能工作。

### 8.2 关于多机同步

资料支持：

1. 对每台电机发送带 `同步标志=1` 的命令
2. 再发送广播 `0xFF` 触发同时动作

这个功能很适合“定位动作”或“严格同时启动”。

但对平衡车来说，我建议：

- `V1` 先不用每周期同步触发
- 先直接顺序发两个速度命令

原因：

1. 双电机命令发送时间差在高波特率下很小。
2. 先减少协议复杂度，更容易把平衡环调起来。
3. 如果后续发现左右轮时序差带来明显偏航，再引入同步触发模式。

建议先按模块拆分，而不是把逻辑全写在 `main.cpp`。

建议目录：


### 9.1 模块职责

`imu_mpu6050.cpp`

- 初始化 MPU6050
- 读取原始 accel/gyro
- 输出姿态解算所需数据

`motor_emm_v5.cpp`

- 封装 `0xF3 / 0xF6 / 0xFD / 0xFE / 0x35 / 0x36 / 0x3A / 0x43`
- 管理地址、校验、串口发送接收、超时

`balance_controller.cpp`

- 根据姿态角和角速度计算平衡输出

`speed_controller.cpp`

- 根据期望速度和轮速反馈计算速度补偿

`safety_manager.cpp`

- 检查倾角过大、通信超时、IMU 异常、低压、堵转
- 触发停机

### 9.2 Arduino on ESP32-S3 的任务划分

建议使用 FreeRTOS 任务，而不是全部堆在 `loop()` 中。

推荐任务：

1. `imu_task`：高优先级，固定周期 2ms
2. `control_task`：高优先级，固定周期 5ms
3. `motor_task`：中优先级，负责串口收发
4. `telemetry_task`：低优先级，日志/上位机输出
5. `safety_task`：中优先级，周期 10ms

如果你想先快速验证，也可以先单线程循环做出第一版，但第二版最好拆任务。

### 9.3 串口在线调参与自动整定机制

建议在本项目中明确区分两类 PID：

1. `整车主控 PID`
2. `Emm_V5.0 驱动内部 PID`

这两类 PID 的作用不同，调参策略也不同。

`整车主控 PID` 是 ESP32-S3 上真正决定平衡效果的参数，至少包括：

- `Angle.Kp / Ki / Kd`
- `Speed.Kp / Ki`
- `Turn.Kp`
- 以及必要时的滤波参数、死区、限幅

`Emm_V5.0 驱动内部 PID` 是驱动器自身的位置环参数，资料中支持：

- 读取 PID 参数：`0x21`
- 修改位置环 PID 参数：`0x4A`

但对平衡车来说，不建议在运行中高频动态修改驱动内部 PID。原因是：

1. 平衡主环的主要控制器在 ESP32 上，而不是在电机驱动器里。
2. 运行中频繁改驱动内部 PID，会引入额外不确定性，问题定位会很困难。
3. 第一阶段应把驱动内部 PID 视为“相对固定的执行层参数”，只在单电机台架测试时做少量修正。

因此本方案建议：

- `在线自动调参` 主要针对 `ESP32 上的平衡车主控 PID`
- `Emm_V5 内部 PID` 仅保留读写接口，不作为第一阶段自动整定对象

### 9.4 双串口职责划分

为了支持在线调参，串口职责必须分离：

1. `Serial`：USB 调试串口，用于上位机参数下发、遥测回传、日志输出
2. `Serial1`：电机总线串口，用于和两个 Emm_V5.0 通讯

不建议把调参串口和电机总线共用，原因很直接：

1. 调参日志会干扰电机控制时序
2. 电机协议帧和调试文本混在一起后很难排障
3. 平衡控制对时序敏感，必须保证电机总线尽量干净

### 9.5 在线调参机制的目标

该机制的目标不是“一键神奇整定”，而是建立一个安全、可回退、可观察的闭环调参流程。

目标分三层：

1. `手动在线调参`
2. `半自动辅助调参`
3. `自动搜索/自动整定`

建议按顺序实现，不要一开始就直接做全自动。

#### 第一层：手动在线调参

上位机通过 USB 串口发送新 PID 参数，ESP32 在运行中即时生效。

需要支持：

- 读取当前参数
- 修改单个参数
- 修改一组参数
- 临时生效
- 保存到 NVS
- 恢复上次稳定参数

这是第一阶段必须实现的能力。

#### 第二层：半自动辅助调参

ESP32 持续回传状态量，上位机根据状态指标给出“建议增减”。

例如：

- 振荡明显，则减小 `Angle.Kp` 或增大 `Angle.Kd`
- 站不住且反应慢，则增大 `Angle.Kp`
- 能立住但持续前后跑，则调 `Speed.Kp / Ki`

这一层的本质是“规则驱动”，而不是完全自动搜索。

#### 第三层：自动搜索/自动整定

上位机根据遥测数据自动计算性能指标，并主动下发新参数。

例如：

- 目标函数 = 倾角绝对值积分 + 轮速抖动 + 饱和次数 + 倾倒惩罚
- 在限定范围内对 PID 参数做搜索
- 保留表现更好的参数组

这一步可以做，但必须建立在前两层稳定后。

### 9.6 建议回传的状态量

为了让串口调参真正可用，ESP32 需要周期性回传结构化状态，而不是只打印几行文本。

建议每 `10ms~20ms` 回传一次核心状态：

1. `ts_ms`
2. `pitch`
3. `gyro`
4. `pitch_target`
5. `left_rpm_target`
6. `right_rpm_target`
7. `left_rpm_actual`
8. `right_rpm_actual`
9. `balance_output`
10. `speed_output`
11. `turn_output`
12. `output_saturated`
13. `motor_state_left`
14. `motor_state_right`
15. `fault_code`

如果要做自动整定，还建议增加：

1. `angle_abs_integral`
2. `angle_peak`
3. `rpm_ripple`
4. `recovery_time_ms`
5. `fall_event_count`

这些量不是每个周期都要重新计算后回传明文，但至少应能由 ESP32 统计并周期上报。

### 9.7 参数下发协议建议

建议使用简单的结构化协议，不要用随意的纯文本命令。

第一版可直接用 `JSON 行协议`：

```json
{"cmd":"set_pid","group":"angle","kp":38.0,"ki":0.0,"kd":0.92}
{"cmd":"set_pid","group":"speed","kp":0.45,"ki":0.02}
{"cmd":"get_pid"}
{"cmd":"save_pid"}
{"cmd":"rollback_pid"}
{"cmd":"set_mode","mode":"assist_tune"}
```

ESP32 回包示例：

```json
{"type":"ack","cmd":"set_pid","ok":true}
{"type":"pid","angle":{"kp":38.0,"ki":0.0,"kd":0.92},"speed":{"kp":0.45,"ki":0.02},"turn":{"kp":0.80}}
{"type":"telemetry","ts":123456,"pitch":1.23,"gyro":-4.5,"l_rpm_t":120.0,"r_rpm_t":118.0,"l_rpm":110.0,"r_rpm":112.0,"sat":0,"fault":0}
```

原因：

1. PC 端开发快
2. 人眼可读，抓包容易
3. 前期调试效率高

后续如果串口带宽不足，再切换为二进制帧。

### 9.8 参数生效策略

在线修改 PID 时，不能“收到就立刻乱写”，需要明确参数生效边界。

建议：

1. 新参数先写入 `pending_pid`
2. 在控制周期边界统一替换为 `active_pid`
3. 替换时清理必要的积分项或做受控切换
4. 仅当姿态角、输出值、故障状态满足条件时，允许应用新参数

推荐的安全门限：

- `|pitch| < 10°` 时允许热更新
- 无故障锁定
- 电机不在急停态

如果条件不满足：

- 先缓存参数
- 等系统回到安全窗口再应用

### 9.9 自动整定状态机建议

自动整定建议做成状态机，而不是写成一个随意脚本。

推荐状态：

1. `Idle`
2. `ManualTune`
3. `AssistTune`
4. `AutoTunePrepare`
5. `AutoTuneRunning`
6. `AutoTuneEvaluate`
7. `AutoTuneApply`
8. `AutoTuneRollback`
9. `FaultLock`

各状态要点：

- `ManualTune`：用户手动改参数，系统实时生效
- `AssistTune`：系统只给建议，不自动改
- `AutoTuneRunning`：按限定步长试探参数
- `AutoTuneEvaluate`：计算该组参数的稳定性评分
- `AutoTuneApply`：只保留更优参数组
- `AutoTuneRollback`：一旦接近失稳，立即回退到上次稳定参数

### 9.10 自动整定评分指标建议

如果后续要做“自动调整参数”，必须先定义什么叫“更好”。

建议用综合评分，而不是只看单一误差：

```text
score =
  w1 * angle_abs_integral
+ w2 * angle_peak
+ w3 * rpm_ripple
+ w4 * output_saturation_count
+ w5 * recovery_time_ms
+ w6 * fall_penalty
```

含义：

- `angle_abs_integral` 越小越好，表示整体更稳
- `angle_peak` 越小越好，表示冲击后摆动更小
- `rpm_ripple` 越小越好，表示轮子不过度抖动
- `output_saturation_count` 越少越好，表示控制器没总在打满
- `recovery_time_ms` 越小越好，表示恢复更快
- `fall_penalty` 极大，表示倾倒直接判定该组参数不可用

### 9.11 针对平衡车的自动调参约束

自动调参不能无边界搜索，必须加硬限制。

建议对 PID 搜索范围先做约束：

- `Angle.Kp`：只允许在一段有限范围内变化
- `Angle.Kd`：步长小于 `Kp`
- `Angle.Ki`：第一阶段默认固定为 `0` 或很小
- `Speed.Ki`：必须有积分限幅
- 每次只改一小步，不允许多参数同时大步跳变

第一阶段推荐的自动整定策略：

1. 固定 `Ki = 0`
2. 先找 `Angle.Kp`
3. 再补 `Angle.Kd`
4. 平衡稳定后再调 `Speed.Kp / Ki`

不要一开始同时搜索 `Kp / Ki / Kd / Speed / Turn`，那样几乎一定会失控。

### 9.12 与 Emm_V5.0 驱动的联动策略

自动调参过程中，Emm_V5.0 驱动层建议保持“尽量固定”。

建议固定的参数：

1. `速度模式 0xF6`
2. `acc = 0`
3. `UartBaud = 256000 或 512000`
4. `Checksum = 0x6B`
5. `Response = Receive` 或稳定后改 `None`

只读不常改的驱动反馈：

1. 实时速度 `0x35`
2. 实时位置 `0x36`
3. 状态标志位 `0x3A`
4. 系统状态 `0x43`

只建议在专项测试时读写的驱动内部 PID：

1. 读取 PID 参数 `0x21`
2. 修改位置环 PID 参数 `0x4A`

结论是：

- 自动调参的主战场在 `ESP32 主控 PID`
- Emm_V5.0 更像“带反馈的执行器”
- 不要在平衡运行时把两层 PID 同时自动调

### 9.13 数据存储与回滚策略

建议至少保留三组参数：

1. `factory_pid`：人工确认可站立的基准参数
2. `active_pid`：当前运行参数
3. `candidate_pid`：自动整定候选参数

保存策略建议：

1. 新参数先做临时运行
2. 连续通过若干轮评估后，再允许覆盖 `factory_pid`
3. 一旦触发倾倒、急停、堵转或通信异常，立即回滚到 `factory_pid`

参数保存位置建议使用：

- `NVS` 保存主控 PID
- 驱动内部 PID 不在自动整定流程中频繁持久化

### 9.14 第一阶段建议的实现顺序

建议按下面顺序实现：

1. 先做 `get_pid / set_pid / save_pid / rollback_pid`
2. 再做结构化 `telemetry` 回传
3. 再做上位机实时曲线显示
4. 然后做“规则驱动”的半自动建议
5. 最后才做真正的自动搜索

这个顺序更稳，因为你先把“可观测”和“可回退”做好，后面自动整定才不会变成盲调。

## 10. 启动与安全策略

### 10.1 上电流程

建议上电状态机：

1. 系统上电
2. IMU 初始化与静止零偏标定
3. 电机串口握手与地址确认
4. 电机使能
5. 检查姿态角是否在允许范围内
6. 进入待立起状态
7. 手扶车体到近平衡点后进入闭环

### 10.2 保护条件

满足任一条件立即停机：

1. 俯仰角绝对值超过 `25°~35°`
2. IMU 数据超时
3. 电机通信超时
4. 电机状态出现堵转保护
5. 电池电压低于阈值

停机动作建议：

1. 先下发两个电机 `立即停止 0xFE`
2. 再执行电机使能关闭
3. 进入故障锁定，等待人工复位

## 11. 调试顺序

建议严格按下面顺序推进，不要跳步：

1. 单独打通 MPU6050 读数和姿态角显示
2. 单独打通 1 个电机的串口速度控制
3. 单独读取 1 个电机的实时速度和状态位
4. 打通双电机独立控制
5. 做轮子悬空状态下的左右轮速度跟随测试
6. 做车架落地但扶持状态下的小角度闭环
7. 再做完全放手平衡

这是必须的，因为你一旦把 IMU、双电机、平衡算法同时上车，定位问题会很慢。

## 12. 关键风险

### 12.1 通讯延迟风险

如果波特率太低、每周期查询太多状态、每次都等待完整返回帧，平衡环会发软。

对策：

- 波特率先升到 `256000` 以上
- 控制环只发速度命令
- 状态读取降频

### 12.2 机械共振风险

闭环步进虽然比普通步进强很多，但仍然比直驱电机更容易受结构振动影响。

对策：

- 车体刚性优先
- 轮胎别太软
- 先降低控制带宽，再逐步提增益

### 12.3 IMU 干扰风险

电机电流、开关电源、地线回路都可能污染 MPU6050。

对策：

- IMU 与电机、电源模块保持距离
- 单独布 3.3V 去耦
- I2C 走线短
- 通讯线和动力线分开走

### 12.4 控制目标选错风险

如果直接拿“位置模式”做平衡主执行，很容易调不顺。

对策：

- 主执行始终围绕 `速度模式`
- 位置模式只用于标定或特殊测试

## 13. 第一阶段交付目标

第一阶段建议做到以下里程碑：

1. `ESP32-S3` 能稳定读取 `MPU6050`
2. 能通过 Arduino 封装好的协议控制 `2 个 Emm_V5.0`
3. 能在串口打印：
   - 俯仰角
   - 俯仰角速度
   - 左右轮目标 RPM
   - 左右轮实际 RPM
4. 能扶持站立 3~5 秒

只要达到这一步，后面调参就有基础了。

## 14. 下一步建议

最合理的下一步不是直接写整车平衡算法，而是先做下面三个基础模块：

1. `Emm_V5.0 Arduino 驱动类`
2. `MPU6050 采样 + 互补滤波`
3. `双电机 200Hz 速度指令调度`

等这三块稳定后，再开始接平衡控制器。
